# NEXUS

Adaptive Physics Learning Game

## Problem Statement

PSN018 — AI-Powered Adaptive Learning Game

## What NEXUS Does

NEXUS transforms Physics learning into an adaptive interactive loop: the
player attempts a real physics experiment, NEXUS scores accuracy, success,
and response performance, and a deterministic adaptive engine adjusts
difficulty and content in response — no two learners see the same sequence
of challenges. A server-side AI layer can add a personalized, plain-language
explanation of *why* an attempt went the way it did, without ever touching
scoring or progression.

## Modules

- **Projectile Motion** — Speed & Range, Gravity & Trajectory
- **Newton's Laws** — Force & Acceleration, Net Force, Friction
- **Work & Energy** — Work, Kinetic Energy, Work-Energy Theorem

3 modules, 9 concepts, each with its own mastery score.

## Adaptive Engine

`scripts/adaptive_engine.gd` tracks a 0–1 mastery value per concept (and a
derived value per module) using an EMA of a per-attempt performance score
(accuracy, success, response time). Concept mastery — never overall mastery
— drives both difficulty (`generate_next_challenge`) and progression
(`evaluate_content_transition`): a concept is reinforced while mastery is
low, advances once it crosses a mastery threshold, and a module hands off
to the next only once every concept in it is mastered. This logic is
entirely deterministic and untouched by the AI layer below.

## AI Learning Insights

The adaptive engine decides *what challenge comes next*. A separate,
server-side AI layer decides *how to explain* the attempt that just
happened — it never sees or influences mastery, difficulty, or
progression. Flow:

```
Player → Godot game → Adaptive Engine → Structured Learning Event
       → AI Insight Service (Next.js API route) → Personalized explanation → Player
```

- `scripts/challenge_manager.gd` posts a structured event (module, concept,
  target/actual values, performance, success, mastery before/after,
  difficulty) to the surrounding website via `window.postMessage`, only
  when running as a Web export inside a browser. This is one-way and
  non-blocking — the result panel and mastery update happen immediately in
  Godot regardless of whether anything is listening.
- `website/src/app/api/insight/route.ts` receives that event server-side
  and calls `website/src/lib/insight.ts`, which attempts a live LLM call
  **only if** `LLM_API_KEY`, `LLM_BASE_URL`, and `LLM_MODEL` are all set;
  otherwise — or if the call fails, times out, or returns something that
  doesn't parse — it falls back to deterministic, rule-based logic that
  uses the same real numbers. The UI never knows which path produced the
  text; a small "Generated by NEXUS's built-in insight logic" note appears
  only on the fallback.
- No API key is read, stored, or referenced on the client, in Godot, or in
  version control, anywhere in this project.

## Technology

- Godot 4.7.2 (Compatibility renderer) — 3D engine and physics simulation
- WebAssembly / Godot Web export — the game runs in-browser, unmodified
- Next.js 16 (App Router) + TypeScript + Tailwind CSS — the product website
- A generic OpenAI-compatible chat-completions call for the optional AI
  insight layer, with a deterministic fallback (no LLM call has been
  tested live in this environment — see below)
- Vercel — target deployment platform

## Running the Godot game

Open `project.godot` in Godot 4.7.2 (Compatibility renderer). Press Play to
run natively, or use **Project → Export** to produce a Web build.

> **Export templates**: this development environment did not have Godot
> Web export templates installed, so `website/public/game/` currently
> contains an earlier Web build (predating the most recent visual pass).
> Install the matching Godot 4.7.2 export templates, re-export to
> `build/web/`, then copy the output into `website/public/game/` before a
> production deploy.

## Running the website locally

```bash
cd website
npm install
npm run dev       # http://localhost:3000
```

Production build (also what Vercel runs):

```bash
cd website
npm run build
npm run start
```

The Godot Web build must exist under `website/public/game/` (see above) for
the Play page to load a real game rather than the fallback message.

### Enabling live AI insights (optional)

```bash
cd website
cp .env.example .env.local
# then set LLM_API_KEY, LLM_BASE_URL, LLM_MODEL in .env.local
```

All three must be set together, or the insight endpoint always uses its
deterministic fallback — this is expected, safe behavior, not an error.

## Deploying to Vercel

1. Import this repository into Vercel.
2. Set the project's **Root Directory** to `website/`.
3. Optionally set `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` as encrypted
   Environment Variables in the Vercel project settings for live AI
   insights; omit them to run on the deterministic fallback.
4. Framework preset: Next.js (auto-detected).

The site sets `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp` site-wide (see
`website/next.config.ts`) because the Godot build uses threads, which
require `SharedArrayBuffer`, which requires a cross-origin-isolated page.

## What this project intentionally does not do (yet)

- No live LLM call has actually been made or tested in this environment —
  no credentials were available. The full adapter and fallback are
  implemented and tested; live invocation requires `LLM_API_KEY` (see
  above) and has not been exercised end-to-end.
- The website has not been deployed to Vercel yet.
- The embedded Web build is not the latest Godot export (see note above).
- 3D vs. 2D presentation has not been re-evaluated — the game remains 3D,
  as instructed.
